# Curator

A grounded, tool-using **multi-agent conversational recommender** for research papers —
built to be measured. Ask it for papers in plain language across multiple turns; every
recommendation is traceable to a retrieved abstract, and every claim in this README is
regenerated by `eval/report.py` from a run directory you can open.

```
you › any good work on retrieval augmented generation for legal text?
curator › Three papers here are directly on point, all post-2023 …
  2401.xxxxx — introduces the chunking scheme the other two build on  [2401.xxxxx]
  2405.xxxxx — the only one that evaluates citation faithfulness      [2405.xxxxx]
  312 ms · 4 llm calls · 3 tool calls · 1 critic round

you › same but only since 2024 and skip the surveys
curator › …
```

## Why this exists

Anyone can wire an LLM to a vector store. The interesting engineering is in the parts
that stop it being wrong: a verification loop with a bound on it, a tool surface with a
schema, citations that are checked rather than requested, and an eval harness that can
tell you whether last week's change helped.

## Architecture

```
START ─► router ─┬─► explainer ─► END           chitchat: retrieval never wakes up
                 │
                 └─► retriever ─► critic ─┬─► explainer ─► END
                        ▲                 │
                        └─────────────────┘   revise, bounded by max_critic_rounds
                        
   retriever ──MCP──► curator-tools server ──► hybrid index (BM25 ⊕ dense, RRF)
                                          └──► user profile store
```

**router** — intent (`recommend | refine | compare | explain | chitchat`) plus slot
extraction. Three interchangeable implementations behind one type: keyword rules, a
prompted chat model, and a QLoRA-tuned 0.6B model. Same interface, so the comparison is
a config flag.

**retriever** — a bounded tool-calling loop. It is handed the tool schemas *discovered*
from the MCP server, not a Python function; it picks the next call, the loop validates
the name and arguments against the advertised JSON schema, executes, and feeds the
observation back. Step budget: 4.

**critic** — the reason this is a graph and not a chain. A deterministic constraint pass
runs first (year and survey filters are arithmetic, not a job for a model), then a model
pass checks the set can support an answer. `revise=true` sends control *backwards* to
the retriever with a hint. `max_critic_rounds` caps the cycle; the round count is in
every trace.

**explainer** — writes the reply, then `enforce_grounding` drops any recommendation
whose id was never retrieved. The drop rate is reported, not silently swallowed.

Everything crossing an agent boundary is a Pydantic model (`src/curator/schemas.py`).
A malformed generation is a caught `ValidationError` with one repair attempt, then a
deterministic fallback — never a crash and never a silently wrong turn.

## Quickstart

```bash
pip install -e ".[dev]"

make test                 # 26 tests, offline: no GPU, no network, no API key
make eval CONFIG=configs/ablations/ci_mock.yaml   # full graph, deterministic backend

# the real thing
ollama pull qwen3:4b
make corpus               # arXiv API -> data/corpus.jsonl
make index                # BM25 + bge-small embeddings
make chat
```

## Deployment paths

One interface (`src/curator/llm.py`), four backends, switched by config or env var:

| backend | what it is | when |
|---|---|---|
| `ollama` | local dev, `ollama serve` | default |
| `openai_compat` | vLLM, `vllm serve Qwen/Qwen3-4B-Instruct` | throughput, batching |
| `hf_local` | transformers + PEFT adapter, 4-bit NF4 | the tuned router |
| `mock` | deterministic, rule-matched | CI and tests |

```bash
make serve-vllm
CURATOR_LLM_BACKEND=openai_compat CURATOR_LLM_BASE_URL=http://localhost:8000/v1 make eval
```

Running the identical eval against two backends is the point: it shows the numbers are a
property of the system, not of one server.

## The MCP tool server

`curator-tools` exposes `search_papers`, `get_paper`, `similar_papers`,
`get_user_profile`, `update_user_profile`. The agent code never imports the retriever —
it lists tools at runtime and calls them by name, and the retriever's system prompt is
*generated* from that discovery, so adding a tool needs no prompt edit.

It runs standalone over stdio or streamable-http, so the same server is usable from any
MCP client:

```bash
make serve-mcp        # or: python -m curator.tools.server --http
make tools            # what the agent sees
```

## Evaluation

`make eval` writes an immutable run directory: resolved config, its fingerprint, git SHA
and dirty flag, dependency versions, per-example records, and aggregates. Temperature is
0 and seeds are set everywhere.

Four metric families, because "it works" is not a number:

| family | metrics |
|---|---|
| retrieval | recall@k, nDCG@k, MRR |
| routing | macro intent F1, slot accuracy |
| generation | groundedness, hallucinated-id rate, constraint-violation rate |
| systems | p50 latency, LLM calls/turn, tool-call validity, critic-loop rate |

Macro F1 rather than accuracy, deliberately: `chitchat` is 15% of turns and an
accuracy-optimal router that never predicts it would be useless.

```bash
make eval-all      # every config in configs/ablations/, then regenerate RESULTS.md
```

`RESULTS.md` is generated. A number in this README that cannot be regenerated is a
number that should not be in this README.

### Ablations the harness answers

| config | question it isolates |
|---|---|
| `single_agent` | what does the multi-agent split buy over one prompt? |
| `no_critic` | is it the split, or the verification gate? |
| `bm25_only` / `dense_only` | does hybrid fusion actually beat either retriever? |
| `router_rules` | can a keyword baseline match the model? (often, partly — say so) |
| `router_lora` | does a 0.6B QLoRA adapter beat prompting a 4B model? |
| `vllm` | do the numbers survive a change of serving stack? |

## The fine-tuned router

```bash
make train-router
```

`train/build_router_data.py` generates the SFT set combinatorially over intents, topics
and constraint phrasings, with the eval split drawn from **disjoint topics** so a good
score cannot come from memorising topic strings. `train/train_router_qlora.py` is TRL
`SFTTrainer` + PEFT `LoraConfig` (r=16, α=32, attention + MLP projections) over a 4-bit
NF4 base — about 6 GB of VRAM. `train/eval_router.py` scores rules vs prompted-4B vs
base-0.6B vs tuned-0.6B on the held-out split, so a change in end-to-end numbers can be
attributed to the router rather than guessed at.

## Reliability, concretely

Not a section of adjectives — these are the mechanisms and where they live:

- **bounded everything**: tool steps (4), critic rounds (2), LangGraph `recursion_limit`
  as a last-resort breaker. A mis-wired edge cannot spin.
- **tool failure is data**: `Toolbox.call` never raises. Errors arrive as `ToolResult`,
  get counted, and are handled by the loop.
- **schema-validated dispatch**: an unknown tool name or a missing required argument is
  rejected before execution and fed back as an observation.
- **fail open, but visibly**: a broken critic passes the answer through with a note; a
  failed writer falls back to a template that is still cited.
- **grounding enforced, not requested**: hallucinated ids are dropped and counted.
- **deterministic first**: constraint checks are arithmetic and run before any model.
- **CI gates on metrics**: recall and groundedness floors, hallucination ceiling. A PR
  that makes the system less grounded fails the build.

## Honest limitations

- The committed fixture corpus is **synthetic** (`data/README.md`). Numbers on it are
  wiring checks. Real results need `make corpus` and hand-judged relevance.
- Relevance judgements are pooled, so recall is recall *of the pool*.
- The critic is the same model family as the writer, which is a known weakness of
  model-as-judge setups: shared blind spots. A cross-family critic is the obvious next
  experiment and the harness would score it unchanged.
- Single-user profiles on local JSON. Nothing here is multi-tenant.
