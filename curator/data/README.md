| file | committed | what it is |
|---|---|---|
| `fixture_corpus.jsonl` | yes | 30 **synthetic** records (ids `FIX-*`) generated by `scripts/make_fixture_corpus.py`. Six disjoint topic clusters so retrieval quality is measurable offline. |
| `corpus.jsonl` | no | The real corpus. `make corpus` fetches it from the arXiv API. |
| `index/` | no | Built by `make index`. Rebuild rather than commit. |
| `router/` | no | SFT splits from `train/build_router_data.py`. |

## The fixture records are not real papers

They carry `SYNTHETIC FIXTURE RECORD` in the abstract and `example.invalid` URLs. They
exist so `make test` and `make eval` run with no network, no GPU and no API key, and so
the eval harness can be tested against known-correct relevance judgements.

**Numbers computed on the fixture corpus are wiring checks, not results.** Anything you
report should come from `make corpus` plus real relevance judgements.

## Getting real judgements

`relevant_ids` in `eval/golden.jsonl` is the expensive part of any retrieval eval, and
there is no shortcut worth taking. The honest procedure:

1. Write 60–100 queries in the shapes users actually type, covering every intent.
2. Pool candidates: for each query take the top 20 from BM25, from dense, and from the
   fused ranking. The union is your judging pool (~40 unique per query).
3. Judge the pool yourself, binary relevant/not, in one sitting with a written rubric.
4. Re-judge 10% a week later and report your own agreement. If it is below ~0.8 the
   rubric is too vague to build on, and every downstream number inherits that noise.
5. Record judged-pool depth in the run metadata — recall is only recall *of the pool*.

Pooling biases against a retriever that was not in the pool, so if you add a third
retriever later, re-pool. Say so in the README rather than quietly not doing it.
